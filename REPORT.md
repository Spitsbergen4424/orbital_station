# Подсистема управления космической станцией

## Описание

В проект добавлена подсистема интерактивного управления космической станцией.

Она позволяет управлять установленными модулями с помощью текстовых команд: строить, активировать, перемещать, повреждать и ремонтировать модули, распределять энергию, запускать исследования и просматривать состояние станции.

Новая часть использует четыре паттерна проектирования:

- **Facade** — единый интерфейс управления;
- **Mediator** — координация взаимодействия компонентов;
- **Command** — представление операций в виде отдельных объектов;
- **Chain of Responsibility** — обработка пользовательских команд.

Для журналирования действий используется существующий `LoggingProxy`.

## Архитектура

Пользователь взаимодействует с программой через консоль. Введённая строка передаётся в `StationFacade`, который запускает цепочку обработчиков.

После определения типа команды создаётся соответствующий объект `Command`. Он выполняет операцию через `StationMediator`.

Посредник взаимодействует с `CommandCenter` и объектами модулей, не заставляя пользовательский интерфейс обращаться к ним напрямую.

Общая схема:

```text
Пользователь
    |
    v
main()
    |
    v
StationFacade
    |
    v
Handler Chain
    |
    v
Конкретный Handler
    |
    v
StationFacade
    |
    v
Command
    |
    v
StationMediator
    |
    v
CommandCenter
    |
    v
Station / Module
    |
    v
Результат операции
```

Подробная UML-диаграмма находится в файле [`UML.md`](UML.md).

## Реализованные паттерны

### 1. Facade — фасад

**Класс:** `StationFacade`

Фасад предоставляет единый интерфейс для выполнения пользовательских операций.

Он скрывает внутреннюю структуру системы и не требует от пользователя знания о том, как устроены командный центр, модули и посредник.

Основные операции:

- активация и деактивация;
- перемещение;
- повреждение и ремонт;
- распределение энергии;
- запуск исследований;
- строительство модулей;
- получение состояния станции.

Пользователь взаимодействует только с фасадом, а тот организует выполнение запроса.

### 2. Mediator — посредник

**Класс:** `StationMediator`

Посредник координирует взаимодействие модулей и командного центра.

Он используется при выполнении операций, связанных с управлением модулями, энергией, повреждениями и исследованиями.

Например, при запуске исследования посредник проверяет тип модуля, его состояние и возможность получить необходимую энергию.

Это позволяет централизовать взаимодействие и не связывать модули друг с другом напрямую.

### 3. Command — команда

**Базовый класс:** `Command`

Каждая пользовательская операция представлена отдельным объектом команды.

Реализованы следующие команды:

- `ActivateModuleCommand`;
- `DeactivateModuleCommand`;
- `MoveModuleCommand`;
- `RepairModuleCommand`;
- `DamageModuleCommand`;
- `DistributeEnergyCommand`;
- `StartResearchCommand`;
- `BuildModuleCommand`;
- `StatusCommand`.

Общий интерфейс выполнения задаётся методом `execute()`.

Команда хранит необходимые параметры операции и обращается к `StationMediator`.

Такое разделение позволяет отделить обработку ввода от логики выполнения действий.

### 4. Chain of Responsibility — цепочка обязанностей

**Базовый класс:** `Handler`

Цепочка обработчиков используется для разбора текстовых команд.

Каждый обработчик отвечает за определённую команду. Если текущий обработчик не распознаёт запрос, он передаёт его следующему элементу цепочки.

Реализованы обработчики:

- `ActivateHandler`;
- `DeactivateHandler`;
- `MoveHandler`;
- `RepairHandler`;
- `DamageHandler`;
- `EnergyHandler`;
- `ResearchHandler`;
- `BuildHandler`;
- `StatusHandler`;
- `HelpHandler`;
- `ExitHandler`.

Цепочка позволяет добавлять новые команды без необходимости помещать всю логику разбора в один большой блок условий.

## Возможности

### Управление модулями

- Строительство новых модулей.
- Активация и деактивация.
- Перемещение между позициями станции.
- Повреждение.
- Ремонт.
- Просмотр состояния отдельного модуля.

### Управление станцией

- Распределение доступной энергии.
- Запуск исследований.
- Просмотр общей статистики.
- Контроль состояния модулей и ресурсов.

### Журналирование

Действия пользователя и события системы записываются через `LoggingProxy`.

## Команды управления

| Команда | Назначение |
|---|---|
| `build <type> "<name>"` | Построить модуль |
| `activate <index>` | Активировать модуль |
| `deactivate <index>` | Деактивировать модуль |
| `move <from> <to>` | Переместить модуль |
| `damage <index>` | Повредить модуль |
| `repair <index>` | Отремонтировать модуль |
| `energy <index> <percent>` | Выделить энергию модулю |
| `research <index>` | Запустить исследование |
| `status` | Показать общую статистику |
| `status <index>` | Показать состояние модуля |
| `help` | Показать список команд |
| `exit` | Завершить программу |

**Примечание:** индексы модулей начинаются с нуля. После перемещения порядок модулей изменяется, поэтому перед выполнением следующей команды следует учитывать их актуальные индексы.

## Примеры использования

### 1. Создание и активация модулей

```text
build solar "Солнечная панель"
build crew "Жилой отсек А"
activate 0
activate 1
status
```

Результат:

- построены два модуля;
- оба модуля активированы;
- выведена статистика командного центра.

### 2. Повреждение и ремонт

```text
damage 0
status 0
repair 0
status 0
```

В результате повреждения прочность модуля уменьшается. После ремонта она восстанавливается до максимального значения.

### 3. Перемещение и исследование

```text
build solar "Солнечная панель"
build crew "Жилой отсек А"
build biology "Биолаборатория"
move 2 0
energy 0 80
research 0
status
```

Сценарий демонстрирует перемещение исследовательского модуля, выделение ему энергии и запуск исследования.

### 4. Взаимодействие через посредника

```text
build reactor "Реактор"
build biology "Биолаборатория"
energy 1 80
research 1
status
```

Сценарий предназначен для проверки взаимодействия исследовательского модуля с системой энергоснабжения через посредника.

## Журналирование

Для записи действий используется существующий `LoggingProxy`.

Пример сообщений:

```text
[2026-11-24 14:35:33] [COMMAND] Выполнение пользовательской команды
[2026-11-24 14:35:33] [CENTER] Добавлен модуль; списана стоимость 20
[2026-11-24 14:35:33] [MODULE] Модуль #1 активирован
```

Журнал позволяет отслеживать последовательность пользовательских действий и события предметной области.

## Результат

В рамках добавленной подсистемы организовано управление космической станцией через текстовый интерфейс.

Четыре паттерна проектирования разделяют ответственность между компонентами:

- фасад упрощает доступ к функциональности;
- цепочка обязанностей разбирает пользовательский ввод;
- команды представляют операции в виде отдельных объектов;
- посредник координирует взаимодействие компонентов.

В результате пользовательский интерфейс отделён от внутренней логики станции, а добавление новых операций может выполняться без существенного изменения существующих компонентов.
